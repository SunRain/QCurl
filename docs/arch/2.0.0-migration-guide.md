# Migrating from QCurl 1.0.0 to 2.0.0

QCurl 1.0.0 remains the published historical release. QCurl 2.0.0 is a deliberate hard-break candidate; downstream code must be rebuilt against the v2 headers and libraries.

## Cache policy APIs

Remove calls to these v1 overloads:

- `parseExpirationDate(const QMap<QByteArray, QByteArray> &)`
- `isCacheable(const QMap<QByteArray, QByteArray> &)`
- `varyHeaderNames(const QMap<QByteArray, QByteArray> &)`

Pass ordered `QList<QCNetworkCacheMetadata::RawHeaderPair>` values instead. Preserve response-header order and duplicate fields when constructing the raw-header list. `headers()` and `setHeaders()` remain observation and storage APIs; they are not alternate policy routes.

## Linking and ABI

Update package and deployment expectations from `SOVERSION 1` to `SOVERSION 2`. The Core shared library is `libQCurl.so.2.0.0`.

`QCurl::BlockingExtras` remains an explicit `COMPONENTS BlockingExtras` consumer target, but it is
now an `INTERFACE` target backed by `libQCurl`; do not package or deploy a separate
`libQCurlBlockingExtras`. Component-filtered development packages only need
`BlockingExtrasDevelopment` in addition to the Core runtime/development files.

QCurl 2.0 guarantees source compatibility for the documented Core surface within the 2.x line, but it does not guarantee binary compatibility. Rebuild and relink every downstream consumer after every QCurl update. Do not deploy an existing downstream binary against a different QCurl 2.x build merely because both use `libQCurl.so.2`.

No v2 ABI baseline is part of the 2.0 release. The historical v1 baseline remains historical evidence and must not be copied or relabeled as a v2 baseline.

## Release workflow

Use the v2 release contract and the default `--abi-mode none` release gate. `current` and `promotion-candidate` are reserved for the future stable ABI project and are not 2.0 release requirements. A local readiness result does not create a tag or remote release.
