## 4. 当前发布裁决

当前必须保持：**NOT READY FOR RELEASE**。

原因不是 hard-break 本身。2.0.0 允许删除旧 API 和 ABI，但不允许降低以下不变量：

1. Qt QObject 生命周期、线程归属和异步结果必须可证明。
2. libcurl easy/multi/share 的绑定、解绑和 cleanup 必须以 libcurl 返回码推进。
3. HTTP、缓存、WebSocket、Cookie 和 Diagnostics 的外部可观察行为必须与合同一致。
4. 正式发行库不得携带测试故障注入面以及内部测试 ABI。
5. promotion manifest 必须绑定 `C1`，final manifest 必须绑定 `C2`；两者都要绑定对应工具链、authority、build tree 和报告。

## 5. 当前确认的 P1 findings

### P1-1：旧 authority 与 `R` 失配，且 `C1/C2` 两阶段身份尚未建立

**定位**

- `.helloagents/archive/2026-08/202608011616_qcurl_v2_hard_break_release/contract.json`：`identityBaseline.head`
- `.helloagents/archive/2026-08/202608011616_qcurl_v2_hard_break_release/requirements.md`：冻结候选身份
- `scripts/release_identity.py:22-27, 273-300`

**代码和合同事实**

`release_identity.py` 会把 HEAD、tracked patch、untracked 集合、submodule、toolchain、build capability、commands 和四项 authority 写入 identity。这个机制本身是正确方向，但已归档 contract 的 baseline 仍是 `15f4d2e...`，而审查基准 `R` 是 `0d1e57d...`。旧 identity 与 `R` 不相容，且旧提交不是 `R` 的祖先。当前脚本和 authority 也没有表达 `C1` 负责 promotion、`C2` 负责 final QA 的两阶段身份合同。

**影响**

任何以旧 baseline 生成的 candidate manifest 都不能证明 `R` 的源码、CMake、release script 和测试，更不能证明后续 `C1/C2` 属于同一受控身份链。即使所有 gate 返回 0，promotion 仍可能提升未被本轮 review 覆盖的对象；把 `C1` 直接称为 final candidate 还会使 baseline 变更失去独立提交边界。

**唯一整改路线**

新建 release authority，并把身份转换固定为两阶段：authority 记录 `R` 只是 review baseline；整改完成后生成 clean `C1`，以 `C1` 重新生成 tracked/untracked、submodule、toolchain、六棵 build tree capability、commands 和 promotion manifest；copy-only promotion 后创建 `C2`，且 `C2` 必须是 `C1` 的 baseline-only 直接子提交；fresh final QA 和 final manifest 只绑定 `C2`。所有旧证据标记为 stale，不迁移、不拼接、不人工修补 digest。review 文档继续作为 derived data，不加入四项 authority。

**验收条件**

- promotion manifest 的 `identity.head` 与 `C1` 完全相等；final manifest 的 `identity.head` 与 `C2` 完全相等。
- `C2^` 与 `C1` 完全相等，且 `C1..C2` 的变更路径恰好为 `abi/baseline/qcurl-core-v2.abi.xml`。
- `C1` 的 tracked patch、untracked、submodule、toolchain、六棵 build tree capability、commands 和 promotion artifacts 属于同一次 producer 运行。
- authority 集合恰好为未来新建且有效的 requirements、plan、contract 和 `docs/arch/2.0.0-hard-break-release-contract.md`。
- final QA 从空目录重建六棵树，且所有 final artifacts 绑定 clean `C2`。
- HEAD、文件、submodule、toolchain、command、build capability 和 artifact 中任一项漂移都会使 verify 非零。

### P1-2：promotion manifest 缺少 producer-bound、可独立重算的 provenance

**定位**

- `scripts/run_release_gate.py:255-301, 455-468`
- `scripts/release_manifest.py:28-58, 121-193, 196-208`
- `scripts/qcurl_abi_gate.py:300-359, 421-534`

**代码和复现事实**

当前验证器会检查 schema、当前仓库 identity、required gate 结果、artifact 文件 digest 和 manifest canonical payload digest。这能够防止普通内容漂移，但它仍主要验证“manifest 与自己记录的对象是否自洽”。本轮负向复核用手工构造的 promotion manifest 和自洽的 artifact/payload digest 运行现有校验链，得到：

```text
FORGED_PROMOTION_MANIFEST_ACCEPTED
```

这不是 SHA-256 算法失效。问题是当前 gate 没有从 `C1`、规定 producer tree 和规定 command 独立重算 artifact provenance；手工重建一份字段与 digest 自洽的 envelope 仍能穿过验证。

**影响**

promotion 的 PASS 可能只证明“manifest 与所指文件相互一致”，不能证明这些文件来自 `C1` 的固定 release route 和固定 producer。证据链缺少可复核的来源约束。

**唯一整改路线**

将 promotion manifest 固定为 producer-bound、可独立重算的 evidence envelope。每个 artifact 必须绑定 `C1` identity、唯一 producer tree ID、实际 toolchain、规范化命令 argv、输入 digest、输出 path/kind/digest 和 gate report；verifier 必须从 clean `C1`、六棵显式 build tree 和磁盘 artifact 独立重算这些字段，不信任 manifest 自报值。文件 SHA-256 只表示内容完整性。本次 2.0.0 不引入签名系统，也不把 manifest 描述为不可伪造、不可重放。

**验收条件**

- 缺少 producer tree ID、实际 toolchain、规范化命令、`C1` identity 和 artifact provenance 中任一项时 verify 非零。
- library、v1 baseline、candidate snapshot、hard-break report、symbol report 和 manifest path 中任一项被替换时 verify 非零。
- 复现本轮 forged manifest 夹具时必须返回非零，并指出 provenance 缺失、不匹配的具体原因。
- verifier 不依赖 manifest 的生成方式，只接受从 `C1`、实际 producer tree 和固定命令独立重算后完全一致的结果；手工填写但没有真实 producer 输出的 envelope 必须失败。

### P1-3：现有 build-dir 路由混用 producer，缺少六树强身份

**定位**

- `scripts/release_gate_steps.py:19-74`
- `scripts/release_gate_steps.py:128-163`
- `scripts/run_release_gate.py:38-92`
- `scripts/release_package_steps.py:17-109`

**代码和复现事实**

`_test_build_dir()` 在没有显式 `--test-build-dir` 时回退到 `args.build_dir`。即使调用方提供现有三树参数，仍存在以下错误路由：

- `shared_public_api`、`shared_public_api_slow` 和 `shared_package_lifecycle` 使用 `test_build_dir`。
- `static_public_api`、`static_public_api_slow` 和 `static_package_lifecycle` 也使用 `test_build_dir`。
- 只有 static configure/package/build 显式使用 `static_build_dir`。

本轮 full dry-run 已观察到 shared/static consumer 和 lifecycle 命令均指向测试树。测试树与发行树的 capability 可能不同，故“命令返回 0”不能证明发行包被测试。

**影响**

这会把 `BUILD_TESTING=ON` 的 test harness 当成 release producer，掩盖正式 shared/static 安装、导出、pkg-config、consumer 和生命周期问题。它同时破坏 Qt/KDE library 常见的“producer 与 test harness 分离”原则。

**唯一整改路线**

固定为六棵彼此独立、从空目录配置的物理树，不允许复用和 fallback：

| tree ID / 固定目录 | toolchain | 必须显式传入的 capability | 唯一职责 |
| --- | --- | --- | --- |
| `release-shared` / `build-release-shared` | authority 冻结的 GCC 版本 | `BUILD_TESTING=OFF`、`QCURL_BUILD_SHARED_LIBS=ON` | shared install/export/pkg-config/consumer/lifecycle、symbol、string、ABI producer |
| `release-static` / `build-release-static` | 与 release shared 完全相同的 GCC | `BUILD_TESTING=OFF`、`QCURL_BUILD_SHARED_LIBS=OFF` | static install/export/pkg-config/consumer/lifecycle producer |
| `test-shared-gcc` / `build-test-shared-gcc` | authority 冻结的 GCC 版本 | `BUILD_TESTING=ON`、`QCURL_BUILD_SHARED_LIBS=ON` | GCC QtTest、public API、libcurl consistency 和白盒故障注入 |
| `test-shared-clang` / `build-test-shared-clang` | authority 冻结的 Clang 版本 | `BUILD_TESTING=ON`、`QCURL_BUILD_SHARED_LIBS=ON` | Clang QtTest、public API 和编译器交叉验证 |
| `asan-ubsan-lsan` / `build-asan-ubsan-lsan` | authority 冻结的 Clang 版本 | `BUILD_TESTING=ON`、`QCURL_BUILD_SHARED_LIBS=ON`、`-fsanitize=address,undefined,leak` | ASan/UBSan/LSan |
| `tsan` / `build-tsan` | 与 sanitizer 树完全相同的 Clang | `BUILD_TESTING=ON`、`QCURL_BUILD_SHARED_LIBS=ON`、`-fsanitize=thread` | TSan |

release shared/static 的所有 package 证据只消费对应 OFF producer。测试和 sanitizer 证据只消费表中指定的 ON tree。OFF tree 不运行 CTest，直接运行对应的 install/consumer/lifecycle gate。每个 gate 必须接收显式 tree path；缺少路径即在执行前失败。

**验收条件**

- dry-run 对每个 gate 的 tree ID、物理路径、toolchain、capability 和规范化命令有精确断言。
- 六棵目录在本轮 configure 开始前均为空，且配置参数与上表完全一致。
- 实际 test/install/consumer/lifecycle/sanitizer/ABI 报告的 producer tree ID、路径和 manifest 一致。
- release report 不引用 ON tree；test 和 sanitizer report 不冒充 OFF producer。
- 任一 tree path 缺失、跨树路径替换、toolchain 漂移和 capability 漂移都会在执行前失败；不存在 build-dir fallback。

### P1-4：share setup rollback 提前删除映射/计数，并忽略解绑失败

**定位**

- `src/private/QCCurlMultiManagerShareLifecycle.cpp:127-196`
- `src/private/QCCurlMultiManagerShare.cpp:15-54, 232-258, 303-332`

**代码事实**

正常 detach 路径 `releaseShareForEasyHandleLocked()` 会先通过 `CookieOptionAdapter` 设置 `CURLOPT_SHARE=nullptr`，成功后才删除 map、减少 `activeUsers` 并尝试 finalize。这一段是当前实现中正确的事务顺序。

但 `applyShareToEasyLocked()` 的 cookie engine 失败回滚路径先执行：

```cpp
shareContext->activeUsers -= 1;
m_easyToShareContext.remove(easy);
m_easyShareOptionSet.insert(easy, false);
```

随后才尝试 `CURLOPT_SHARE=nullptr`，且忽略该操作的结果。`resetShareOnEasyIfNeeded()` 也直接调用 `curl_easy_setopt()`，不检查 `CURLcode`。`onAccessManagerDestroyedLocked()` 中的直接 `curl_share_cleanup()` 同样没有把返回码纳入状态迁移。相比之下，`maybeFinalizeShareContextLocked()` 已检查 `CURLSHcode` 并在失败时 poison；该局部修复不能覆盖所有 rollback/teardown 入口。

**影响**

当解绑失败时，内部 map/count 可能已经声称 easy 不再绑定，而 libcurl 仍持有 share handle。随后 callback userdata、share context 和 easy 的可达图不一致，导致错误处理、后续 cleanup 和生命周期证明失真。

**唯一整改路线**

把 bind、rollback、detach 和 cleanup 统一为一个以 libcurl 返回码驱动的事务：只有 `CURLE_OK` 的 `CURLOPT_SHARE=nullptr` 才能更新映射和真实绑定计数；也只有 `CURLSHE_OK` 才能释放 share/context、清空 handle。任何失败进入 manager poison，并保留 easy、share、context 和 callback userdata 的可追踪对象图。

**验收条件**

- 注入 setopt/unbind 失败时 map、计数、context 和 share handle 均保持可追踪。
- `CURLSHE_IN_USE` 及其他 cleanup 失败均不得释放 context、清空指针。
- focused QtTest 覆盖 detach failure、cleanup-in-use 和 shutdown cleanup failure。
- ASan/LSan 证明 callback 后置触发不访问已释放 userdata。

### P1-5：promotion 在 digest 验证后重新覆盖 snapshot/report

**定位**

- `scripts/qcurl_abi_gate.py:669-713`
- `scripts/qcurl_abi_gate.py:421-534`

**代码事实**

`command_promote()` 先调用 `verify_promotion_manifest()`，验证 manifest 中的 candidate library、v1 baseline、candidate snapshot、hard-break report、symbol report 和各自 digest。验证通过后，又在 `692-702` 重新运行 `abidw` 和 `abidiff`，覆盖 candidate snapshot 和 old-to-new report，再复制新的 snapshot 到 v2 baseline。

这使得已验证的 artifact 字节不是最终被 promotion 使用的字节。环境、工具链、调试信息、动态库中的任一项在验证后发生变化时，promotion 仍可能生成一份未被原 manifest digest 覆盖的新报告。`manifestPayloadSha256` 只能证明 JSON 自洽，不能自动证明后写入的文件仍与此前 digest 相同。

**影响**

promotion 的输入绑定在最后一步被重新生成路径绕开，candidate snapshot/report 的审计意义被削弱。

**唯一整改路线**

promotion 固定为 copy-only：验证 clean `C1`、promotion manifest 和全部输入 digest 后，只把 manifest 绑定的 candidate snapshot 复制到受控 v2 baseline。promotion 进程禁止调用 `abidw`、`abidiff`，禁止写 candidate snapshot、hard-break report 和 symbol report。candidate、toolchain、command、producer tree、manifest、snapshot 和 report 中任一输入变化都必须立即终止本轮；后续执行从 producer 阶段开始，清空并重建六棵物理树，生成新的 manifest，再重新进入 promotion。

**验收条件**

- promotion 过程中 candidate snapshot/report 不发生写入。
- promotion 的实际进程调用记录中不存在 `abidw`、`abidiff`。
- 任一输入在 verify 后发生变化都会被检测并拒绝。
- 受控 v2 baseline 与 manifest 中 candidate snapshot 字节完全相同。
- promotion 日志记录的 artifact digest 与最终复制对象一致。

### P1-6：required release evidence 未完整绑定 parity、install、sanitizer、TSan 和 lifecycle 报告

- `scripts/run_release_gate.py:201-252, 255-301`

- `scripts/release_package_steps.py:36-109`

**验收条件**

- parity、install/consumer、lifecycle、ASan/UBSan/LSan、TSan、UCE、Doxygen、ABI、symbol 报告中的任一 required 项缺失时 verify 非零。

## 6. 当前确认的 P2 findings

### P2-1：static `BUILD_TESTING=ON` 组合 configure 成功但测试链接失败

**定位与复现**

在 `QCURL_BUILD_SHARED_LIBS=OFF` 且 `BUILD_TESTING=ON` 的静态测试组合中，配置阶段当前成功，但测试链接阶段复现 `CurlFeatureProbe::refreshForTesting()` 未解析符号。该问题不影响合同规定的 `BUILD_TESTING=OFF` 静态发行树，却会让一个看似受支持的测试组合在晚期失败。

**影响**

配置成功给调用者一个错误的可用性信号，降低 Qt/CMake consumer 和 CI 矩阵的确定性。它属于工程边界和反馈问题，不应被夸大为生产库内存安全缺陷。

**唯一整改路线**

`QCURL_BUILD_SHARED_LIBS=OFF + BUILD_TESTING=ON` 明确列为 QCurl 2.0.0 不支持的组合。顶层 CMake 在 options 解析后立即 `message(FATAL_ERROR ...)`；文档与 CI 支持矩阵同步标记为 unsupported；只保留一个负向 configure 测试，断言该组合返回非零并输出固定诊断。不得为该组合扩展 static test-internals target，也不得让它进入构建及链接阶段。

**验收条件**

- 受支持的六树矩阵配置、构建和相应 gate 全部通过。
- `QCURL_BUILD_SHARED_LIBS=OFF + BUILD_TESTING=ON` 在 configure 阶段返回非零和固定错误文本。
- 文档与 CI 只把该组合列为 unsupported，且仅运行负向 configure 测试。
- release static consumer 不依赖 `refreshForTesting()` 等 test-only symbol。

### P2-2：Pool 同步 mutator 在失败路径静默 no-op

**定位**

- `src/QCWebSocketPool.h:176,196,214`
- `src/QCWebSocketPool.cpp:267-294,305-313,360-369`

**代码事实**

`release()`、`clearPool()`、`setConfig()` 当前均返回 `void`。三者在错误线程和 `Destroying` 状态直接返回；`setConfig()` 在非法配置时也直接返回；`release()` 对 null 及非本 Pool 的 socket 同样没有失败结果。与之相对，`acquire()`、`preWarm()` 已能返回完成态 `WrongThread`。因此 Pool 的异步命令有显式结果，同一 public API 的同步 mutator 却把调用失败伪装成成功完成。

**影响**

调用方无法判断配置、清理和归还操作是否真正执行，也无法可靠记录错误、回滚上层状态及编写确定性测试。自动跨线程排队会进一步改变同步 API 的完成时点和对象生命周期，不适合作为修补方案。

**唯一整改路线**

保持 owner-thread-only 合同，不自动排队。`acquire()`、`preWarm()` 的错误线程调用继续返回已完成的 `WrongThread` 结果且不产生 socket 副作用；三个同步 mutator 在 2.0.0 hard-break 中统一改为：

```cpp
[[nodiscard]] bool release(QCWebSocket *socket, QString *error = nullptr);
[[nodiscard]] bool clearPool(const QUrl &url = QUrl(), QString *error = nullptr);
[[nodiscard]] bool setConfig(const QCWebSocketPoolConfig &config, QString *error = nullptr);
```

返回 `true` 表示操作已在 owner thread 同步执行，合法的空清理属于成功 no-op。错误线程、`Destroying`、非法配置、null socket 和非本 Pool socket 统一返回 `false`；调用方传入 `error` 时必须得到稳定、非空的诊断文本。所有现有调用点必须消费 bool 结果；`preWarm()` 内部归还失败时将本次操作完成为现有 `ConnectionFailed`，不得把连接计入 warmed 数量。该 API 不增加新的结果类、signal 和 queued wrapper。

**验收条件**

- 三个 public mutator 均为 `[[nodiscard]] bool + QString *error`，实现和文档签名一致。
- 错误线程调用不排队、不改变 Pool 状态，返回 `false` 和固定诊断。
- `Destroying`、非法配置、null socket、foreign socket 分别有 focused QtTest，均证明无副作用。
- 成功路径返回 `true`；`clearPool()` 面对空集合仍返回 `true`。
- `preWarm()` 内部 `release()` 返回 `false` 时只完成一次 `ConnectionFailed`，warmed 数量不增加。
- `acquire()`、`preWarm()` 保持完成态 `WrongThread` 合同，不新增第二套线程切换路线。

## 7. 已确认的修复与过度设计裁剪

### 7.1 正式库 test hook：旧 P0 结论不成立

上一版根据旧树印象把 `BUILD_TESTING=ON` 与正式 target 的 `QCURL_ENABLE_TEST_HOOKS` 直接等同。当前 `src/CMakeLists.txt:394-420` 显示该宏只定义在 `QCurlTestInternals` 和 `QCurlOtherExtrasTestInternals` 两个 `STATIC EXCLUDE_FROM_ALL` companion target 上。当前 release shared 产物的 `nm -D`/`strings` 对照也没有 `ForTest`、`ForTesting`、`QCURL_TEST_FORCE_*`。

结论：删除旧 P0 finding。仍保留“正式产物纯度”作为 release gate，因为未来 CMake 改动可能重新引入污染，但当前不能把它报告为已证实代码缺陷。

### 7.2 `QCWebSocketPool` 裸指针、析构重入和配置溢出：旧 finding 不再确认

当前实现已具备：

- `QCWebSocketPoolPrivate::PooledConnection::socket` 使用 `QPointer<QCWebSocket>`。
- `QObject::destroyed` 连接到 `onSocketDestroyed()`，清理主索引、反向索引和等待中的 acquire。
- 析构第一步进入 `Destroying`，pending acquire/preWarm 返回 `PoolDestroyed`。
- timer、socket slot、query 和 mutator 都有 owner-thread/Destroying guard。
- `validatePoolInput()` 统一限制 pool size、total connections、preWarm count、idle seconds 和 keepalive 毫秒转换。
- `preWarm(0)` 是成功 no-op，负数和越界返回 `InvalidArgument`。

因此旧的 Pool UAF、析构 future 被取消和 signed overflow 不能继续作为当前已证实 blocker。仍需在 fresh final QA 中保留外部 delete、parent delete、deleteLater、direct signal reentry、timeout 和 keepalive 的回归矩阵；“需要最终证明”不等于“当前已发现缺陷”。

### 7.3 Pool 输入校验已修复，但同步失败反馈仍构成 P2-2

现有 validator 已关闭容量、负数和 timer overflow 的安全边界，因此这些旧缺陷不恢复为 finding。剩余问题是 `release()`、`clearPool()`、`setConfig()` 仍用 `void` 隐藏失败。该问题已升格为 P2-2，并固定采用 `[[nodiscard]] bool + QString *error`；不引入复杂结果类型，不新增跨线程 queued 路线。

### 7.4 不把 SHA-256 描述成签名，不把所有 finding 强制绑定所有 sanitizer

artifact SHA-256 只能证明被验证文件的内容完整性。它不能单独证明生产者、签署者、运行环境真实性。反过来，单项 finding 只需与风险匹配的定点证据；不要求每个小型 API 反馈缺口都运行 ASan/TSan。全局 final release 才需要完整 sanitizer、parity、ABI 和 install 矩阵。

## 9. Qt6、libcurl 和 Qt/KDE library 最佳实践裁决

### 9.1 Qt6 网络编程

- QObject 及其子对象只能在 owner thread 操作；Pool 不自动跨线程排队。`acquire()`、`preWarm()` 在错误线程返回完成态 `WrongThread`；同步 mutator 返回 `false`，调用方传入 `error` 时同时得到 `QString` 诊断；所有错误线程路径均不得产生副作用。
- 异步 API 必须区分 `PoolDestroyed`、`WrongThread`、`InvalidArgument`、取消和传输失败；Qt future 被取消不能替代业务结果。
- `QPointer` 只能解决 QObject 指针失效检测，不能替代索引清理、promise 完成和线程边界；两者必须同时存在。
- timer interval、连接数和预热数量必须在进入 Qt API 前完成有界校验，不能依赖 Qt 版本对非法值的隐式处理。
- install/export/pkg-config/consumer 证据必须来自发行 producer tree，不能从 test harness 借路径。

### 9.2 libcurl binding

- `CURLE_*`、`CURLM_*`、`CURLSH_*` 返回码必须驱动状态迁移；内部计数不能覆盖 libcurl 的真实 ownership。
- easy 仍绑定 share 时，`curl_share_cleanup()` 返回 `CURLSHE_IN_USE` 必须 fail closed，不能清空 callback userdata、伪造解绑成功。
- header slist、callback userdata、body source 和 multi/easy handle 的 backing storage 必须覆盖整个使用期；解绑失败时先保留对象图。
- raw header 必须保留顺序、大小写和重复项；`QMap` 不能作为有损的协议边界。
- QCurl 与 direct libcurl 的 status、body、header、redirect、cache directive、`Vary`、`Date/Age`、304、upload、retry、Cookie 和 WebSocket 结果必须用 live fixture 做 parity proof。

### 9.3 Qt/KDE library 和企业级 C++ 架构

- public header 只承诺真实 public API；private manager、QObject layout、test helper 和 diagnostics hook 不进入 Core ABI。
- shared/static、release/test、Core/Other Extras 的 target 边界必须由 CMake 明确表达，测试 companion 不安装、不进入 package/export/ABI manifest。
- 错误不能用静默 no-op 隐藏；2.0.0 直接 hard-break 三个 Pool 同步 mutator 为 `[[nodiscard]] bool + QString *error`，不保留旧 `void` 签名和 legacy shim。
- release script 必须把 authority、`C1/C2`、六棵 producer tree、commands 和 artifacts 建模为 producer-bound、可独立重算的 contract；“命令返回 0”不是完整证据。
- 不因旧 API 压力保留第二路线、shim 和运行时开关。2.0.0 hard-break 一次性收敛，不把安全及证据缺口延后到发布后。

## 10. 外部可观察一致性：当前不是新 finding，但属于 final gate

以下要求仍是 QCurl 作为 libcurl binding 的发布前置，不应因为本轮没有重新复现 P0/P1 就省略：

### HTTP/Reply

- status code、reason、body bytes、ordered raw headers 与 direct libcurl 一致。
- 重复 `Set-Cookie`、`Cache-Control`、`Vary`、`Date`、`Age` 不被最后值覆盖。
- redirect、stream upload、retry/idempotency、cancel、timeout、reply destroyed 和 manager destroyed 均 exactly once。

### Cache / RFC 9111

- cache admission 只消费 ordered raw response headers。
- `Vary` 使用真实有效的出站 request header。
- `Set-Cookie` 可网络观察但不进入 response cache replay。
- `Date`、`Age`、current-age、freshness 和 304 merge 具有明确饱和及合并边界。
- 磁盘 cache 先做文件大小和字段长度限制，再反序列化损坏输入。

### WebSocket

- CONNECT_ONLY transfer 在 send/recv 使用期留在 multi。
- EAGAIN、partial frame、close frame、socket error 和 cancellation 映射稳定。
- Pool 外部删除、parent delete、deleteLater、timer、keepalive 和 direct signal reentry 均不得留下悬空对象与未完成 future。
- Pool 不自动跨线程排队；异步命令返回完成态错误，同步 mutator 返回 `[[nodiscard]] bool + QString *error`。

### Release / ABI

- release shared/static 分别来自两棵 OFF producer；GCC test、Clang test、ASan/UBSan/LSan、TSan 分别来自四棵独立 ON tree；test hook 只存在于不安装 companion。
- Core dynamic symbol 与 public surface manifest 一致；Other Extras 通过最小 opaque bridge。
- promotion manifest 可从 `C1` 独立重算；final manifest 可从 `C2` 独立重算；报告和 install/consumer 产物具有 stage/tree/path/kind/digest/provenance。
- `C1` 不含 v2 ABI baseline 变化；`C2` 是 `C1` 的 baseline-only 直接子提交；final QA 后不再提交。

## 11. 唯一整改路线

本轮不执行源码整改，只冻结一条后续工程状态机：

```text
R -> remediation -> C1 -> copy-only promotion -> C2 -> fresh final QA
```

1. **以 `R` 新建 authority**：不得复用已归档方案包。新 requirements、plan、contract 和 release contract 明确记录 `R` 只是 review baseline，并固定 P1/P2、六树表、`C1/C2` 身份规则及 required artifacts。旧 `15f4d2e...` 证据全部标 stale。
2. **在 remediation 一次性关闭八项 finding**：统一 libcurl share bind/rollback/detach/cleanup 事务；修正 producer provenance、六树路由、copy-only promotion 和 required evidence；CMake 拒绝 static testing；Pool 三个同步 mutator hard-break 为 `[[nodiscard]] bool + QString *error`。先写负向测试，再修改实现。
3. **运行提交前验证**：使用临时空目录完成 focused tests、release-script 单元测试、CMake 负向 configure 测试和风险匹配的 sanitizer。此阶段只证明整改可提交，不生成 promotion/final manifest，不修改 v2 ABI baseline。
4. **创建 `C1`**：获得本地提交授权后，把 authority、源码、测试、CMake、release scripts 和文档提交为一个 clean implementation/promotion candidate。`C1` 不包含 v2 ABI baseline 变化。
5. **在 clean `C1` 生成 producer evidence**：从空目录建立 P1-3 定义的六棵物理树，执行全部 pre-promotion gate，生成 producer-bound promotion manifest。每项报告绑定 `C1`、tree ID、toolchain、command、path/kind/digest。
6. **执行 copy-only promotion**：在 clean `C1` 上验证 promotion manifest；验证通过后只把已验证 candidate snapshot 复制为 `abi/baseline/qcurl-core-v2.abi.xml`。promotion 内禁止 `abidw`、`abidiff` 和报告重写。
7. **创建 `C2`**：获得 baseline 提交授权后创建 `C1` 的直接子提交。`C1..C2` 只包含 `abi/baseline/qcurl-core-v2.abi.xml`；`C2` 成为唯一 final candidate。
8. **在 clean `C2` 执行 fresh final QA**：再次从空目录建立同一六树拓扑，重跑 QtTest、libcurl consistency、HTTP/cache/WebSocket/Cookie/Diagnostics live parity、public API、install/consumer/lifecycle、ABI、ASan/UBSan/LSan、TSan、UCE、Doxygen、symbol 和 manifest verify。final manifest 只绑定 `C2`。
9. **作出发布裁决**：全部 P1/P2 为 `VERIFIED`、required artifacts 完整、final manifest 重验返回 0 后，状态才可改为 `READY_FOR_RELEASE`。final QA 后不得再产生提交。tag、push、GitHub Release 和资产上传不在本合同内。

步骤 3 失败时停留在 remediation。步骤 5、6 的 producer artifact、digest、报告失败时，丢弃本轮六树和 manifest，从六个空目录对同一 clean `C1` 重跑；冻结输入发生变化时回到步骤 2 并创建新的 `C1`。步骤 8 失败时 `C2` 保持 `NOT READY FOR RELEASE`；candidate 输入不变时丢弃失败报告并从空目录重跑 final QA，任何整改提交都必须重新创建 `C1 -> C2`。所有失败路径均禁止就地修补 manifest、复用 build tree、覆盖已验证报告、提前刷新 baseline、追加 post-QA commit。

## 12. 证伪条件、止损和边界

### 12.1 关闭本轮 finding 所需的证据

必须提供 `C1/C2` 的机器证据，而不是解释和旧日志：

- promotion identity 与 clean `C1` 完全匹配，final identity 与 clean `C2` 完全匹配。
- `C2^` 等于 `C1`，且 `C1..C2` 只包含 v2 ABI baseline。
- share rollback/cleanup 负向测试和 sanitizer 报告。
- forged manifest 负向测试返回非零。
- 六树 dry-run、实际 test/install/consumer/lifecycle/sanitizer 报告的 tree ID、toolchain、capability 和路径完全一致。
- promotion 的调用记录不含 `abidw`、`abidiff`，且最终 baseline 与 manifest candidate snapshot 字节一致。
- required CTest/parity/install/consumer/lifecycle/ASan/UBSan/LSan/TSan/UCE/Doxygen/ABI/symbol 报告任一缺失和任一漂移都会使 verify 非零。
- static unsupported combo 在 configure 阶段明确失败。
- Pool 同步 mutator 对错误线程、`Destroying`、非法输入返回 `false` 和稳定诊断；`acquire()`、`preWarm()` 继续返回完成态 `WrongThread`。

单个 finding 进入 `VERIFIED` 只需要与风险匹配的定点证据；全局 release 仍需要完整 final matrix。

### 12.2 必须立即止损的情况

## 15. 最终结论

本轮复核确认：QCurl 2.0.0 的 hard-break 方向、ordered raw-header cache 路线、Qt6 异步 API 和 Pool `QPointer` 生命周期路线具备合理基础；上一轮部分 P0/P1 属于旧树事实与过度设计，已经分别撤销、降级。release/test/sanitizer 拓扑则必须从模糊三树收敛为六棵显式物理树。

审查基准 `R` 不是 candidate，也没有达到企业级 Qt6/C++ 网络库发布标准。真正未闭合的是 `C1/C2` 身份链、promotion manifest 的 producer-bound 独立重算、六树 release/test/sanitizer 路由、libcurl share rollback 的真实 ownership、copy-only promotion 以及 required evidence 的完整绑定。另有 static testing configure 边界和 Pool 同步 mutator 反馈两项 P2。

因此，当前唯一正确的工程结论是：**QCurl 2.0.0 尚无有效 final candidate，审查基准 `R` 不得发布，状态保持 `NOT READY FOR RELEASE`。** 旧 review、旧 build tree、旧 PASS、手工自洽 manifest、Preview 标签、关闭能力和 legacy shim 都不能替代上述整改、`C1 -> C2` 身份转换及绑定 `C2` 的 fresh final QA。
