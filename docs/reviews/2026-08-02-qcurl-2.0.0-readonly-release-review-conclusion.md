## 一、执行摘要

QCurl 当前不能进入 2.0.0 release candidate。阻断原因不只是 candidate/promotion/final QA 尚未执行，也不是单纯缺少 commit/tag/CI 证据，而是当前正式库、libcurl share 绑定生命周期、WebSocketPool 指针失效协议和 release 证据链本身仍存在可复现或可绕过的缺陷。

当前最重要的结论如下：

1. 默认 `BUILD_TESTING=ON` 构建会把 `QCURL_ENABLE_TEST_HOOKS` 编进正式 `QCurl` / `QCurlOtherExtras` shared library。`libQCurl.so.2.0.0` 已导出 `ForTest/ForTesting` 符号，并包含 `QCURL_TEST_FORCE_*` 环境变量控制面。这是生产可达的故障注入面，不是测试体积问题。
2. `curl_share_cleanup()` 的返回值被忽略，内部 `activeUsers` 又没有绑定到真实 `CURLOPT_SHARE=nullptr` 成功结果。libcurl 独立复现已经证明 easy 仍绑定 share 时 cleanup 返回 `CURLSHE_IN_USE(2)`。当前实现会丢失对旧 share 与 callback userdata 的真实跟踪。
3. `QCWebSocketPool` 内部仍以裸 `QCWebSocket*` 作为主索引、反向索引和成功结果，没有 `QObject::destroyed` 失效协议。调用方合法删除池内 socket 后，pool 后续 `acquire()`、`clearPool()`、keepalive、cleanup 和连接 timeout lambda 都可能解引用旧地址。本轮 ASan 最小复现已经触发 `heap-use-after-free`。
4. `QCWebSocketPool` 析构期间调用 `clearPool()` 并发射 `connectionClosed`，direct slot 可以重入 `acquire()`。现有复现显示重入 future 被 Qt 取消，未得到 `PoolDestroyed` value result，违背当前显式 value-result 合同。
5. release manifest 和 ABI promotion 证据仍可漂移：required artifact 无 digest 时内容变化不会被拒绝；`full`/`promotion`/`final` gate 仍允许空 authority；promotion 没有把 manifest 中记录的 candidate library、v1 baseline、candidate snapshot/report 与命令行输入做 path/digest 绑定。
6. 内部 `QCCurlMultiManager` 仍作为 owner 被纳入 Core public ABI allowlist，`instance()` 与 `runningRequestsCount()` 仍处在正式库导出面；历史 testing-off 对照也确认该内部 owner 并非只由测试宏引入。2.0.0 允许 hard-break，应删除这类内部实现承诺。
7. WebSocket libcurl cleanup 路径忽略 `CURLOPT_HTTPHEADER=nullptr` 返回码，并在 persistent transfer 安全摘除前释放 slist，构成 backing-storage ownership 风险。`CURLINFO_SSL_VERIFYRESULT` 查询失败不会把既有 TLS `CURLcode` 失败变成成功，但会造成详细诊断不可用；两者必须分开定级和修复。
8. Pool 配置 setter 与 `preWarm()` 缺少输入边界。负数和极大值可进入运行路径，极大 count 会直接创建同量 promise/循环，秒到毫秒还存在 signed overflow 风险。`preWarm(0)` 可以定义为成功 no-op，不能未经合同裁决一概视为非法。
9. 活跃方案包把 T5/T6 标记为完成并停在提交授权门，但 required artifact digest、authority cardinality 和 promotion 输入绑定均未成立。真实进度必须退回整改阶段。

因此，当前状态必须保持：**NOT READY FOR RELEASE**。

## 三、历史结论如何并入本轮结论

2026-07-31 的历史审查确立了 QCurl 的企业级底线：Qt6 QObject 生命周期、libcurl multi/easy/share ownership、ordered raw headers、RFC 9111 缓存、磁盘反序列化上限、Cookie 事务语义、UCE fail-closed、public ABI 最小化和默认安装包安全门禁。后续 remediation 与 v2 hard-break 计划解决了其中一部分问题，例如：

- cache 策略路线收敛为 ordered raw header 输入。
- WebSocketPool 的部分 direct signal reentry 矩阵与 Ping/Pong keepalive 证据已建立。
- release manifest authority 的四件套概念已经进入 contract。
- ABI gate 拆成 `current` 与 `promotion-candidate` 两个模式。

但这些进展不能抵消本轮发现的新阻断。原因有三点：

1. **历史 QA 不是当前 release 证据**：当前 HEAD、tracked patch、untracked 文档、CMake 选项、build tree 和 release scripts 已经变化。旧 `86/86`、`101/101`、sanitizer、UCE、ABI 或 Python `41 passed` 只能说明旧快照。

本文因此不重写旧 20 项 finding 的历史价值，但以当前代码事实重新裁决 release 状态。

### P0-1 正式发行库在默认测试构建中混入生产可达测试 hook

**位置**

- `CMakeLists.txt:16`
- `src/CMakeLists.txt:375-379`
- `src/private/QCRequestPipeline_p.h:129`
- `src/private/QCCurlOptionAdapter_p.h:31-42`

**代码事实**

顶层默认 `BUILD_TESTING` 为 `ON`。`src/CMakeLists.txt` 在 `BUILD_TESTING` 为真时直接给正式 `QCurl` 与 `QCurlOtherExtras` target 添加 `QCURL_ENABLE_TEST_HOOKS`：

```cmake
if(BUILD_TESTING)
    target_compile_definitions(QCurl PRIVATE QCURL_ENABLE_TEST_HOOKS)
    target_compile_definitions(QCurlOtherExtras PRIVATE QCURL_ENABLE_TEST_HOOKS)
endif()
```

当前 `build-v2-promotion-shared/src/libQCurl.so.2.0.0` 可观察到如下导出符号：

- `QCurl::QCCurlMultiManager::addTransferForTest(...)`
- `QCurl::QCCurlMultiManager::processUnknownDoneForTest()`
- `QCurl::QCNetworkAccessManager::registerSchedulerLaneForTesting(...)`
- `QCurl::QCNetworkRequestScheduler::instanceForTesting()`
- `QCurl::QCNetworkRequestScheduler::setConfigForTesting(...)`
- `QCurl::QCNetworkRequestScheduler::setLaneConfigForTesting(...)`
- `QCurl::QCNetworkRequestScheduler::configForTesting() const`
- `QCurl::QCNetworkRequestScheduler::laneConfigForTesting(...) const`

同一 shared library 的字符串中包含以下环境变量控制面：

- `QCURL_TEST_FORCE_CAPABILITY_ERROR`
- `QCURL_TEST_FORCE_COOKIE_OPTION_ERROR`
- `QCURL_TEST_FORCE_GLOBAL_INIT_ERROR`
- `QCURL_TEST_FORCE_MULTI_FAILURE`
- `QCURL_TEST_FORCE_MULTI_REMOVE_ERROR`
- `QCURL_TEST_FORCE_RUNTIME_LIBCURL_VERSION_NUM`
- `QCURL_TEST_FORCE_SETOPT_ERROR`
- `QCURL_TEST_FORCE_SHARE_OPTION_ERROR`
- `QCURL_TEST_FORCE_SLIST_APPEND_ERROR`

**为什么是 P0**

这是生产行为可被进程环境改变的问题。发行库不能因为 `BUILD_TESTING=ON` 就把故障注入、mock chaos、强制 libcurl option 失败、强制 global init 失败和内部测试入口编入正式 shared target。对库项目而言，测试构建也经常用于打包、安装验证和 CI artifact；只要正式 target 获得该宏，ABI、行为、稳定性和安全边界就已经被污染。

**唯一修复路线**

1. 正式 `QCurl` 与 `QCurlOtherExtras` target 永不定义 `QCURL_ENABLE_TEST_HOOKS`。
2. 复用已经存在的 `QCurlTestInternals` / `QCurlOtherExtrasTestInternals`；白盒 QtTest 与 libcurl consistency 只链接 companion，不再回链受污染的正式库。
3. companion 保持 static、`EXCLUDE_FROM_ALL`、不安装、不进入 CPack、pkg-config 或 public ABI manifest。
4. `BUILD_TESTING=OFF` release tree 提供发行 shared/static library、install、CPack、consumer、symbol、string 和 ABI 证据。
5. `BUILD_TESTING=ON` test tree 提供 QtTest、libcurl consistency、故障注入和 sanitizer 证据；该树中的正式 target 仍必须保持生产纯度。
6. 正式 full gate 显式绑定 release shared、release static 与 test shared 三个 build dir。发行产物、安装、consumer、symbol、string 和 ABI step 只消费 release tree；CTest、libcurl consistency、生命周期与 sanitizer step 只消费 test tree。由于 `BUILD_TESTING=OFF` tree 不注册 CTest，安装/consumer gate 必须直接以 release tree 为 producer，不能对 OFF tree 伪调用 CTest。

**完成标准**

- `nm -D --defined-only` 中没有 `ForTest` / `ForTesting` / test hook owner。
- `strings libQCurl.so*` 和 `strings libQCurlOtherExtras.so*` 中没有 `QCURL_TEST_FORCE_*`。
- 测试仍能通过 companion target 做故障注入。
- 同一个 release manifest 区分并绑定 `BUILD_TESTING=OFF` 发行树与 `BUILD_TESTING=ON` test/companion 证据；不生成可独立漂移的第二份 test manifest。

### P0-2 share handle 的真实 libcurl 绑定与内部 `activeUsers` 脱节

**位置**

- `src/private/QCCurlMultiManagerShare.cpp:15-20`
- `src/private/QCCurlMultiManagerShare.cpp:302-318`
- `src/private/QCCurlMultiManagerShareLifecycle.cpp:40-42`
- `src/private/QCCurlMultiManagerShareLifecycle.cpp:134-136`
- `src/private/QCCurlMultiManagerShareLifecycle.cpp:158-166`
- `src/QCCurlMultiManager.cpp:389-397`

**代码事实**

当前绑定成功后只增加内部计数：

```cpp
shareContext->activeUsers += 1;
m_easyToShareContext.insert(easy, shareContext);
m_easyShareOptionSet.insert(easy, true);
```

释放时却只从内部 map 删除并递减 `activeUsers`，没有先证明 `CURLOPT_SHARE=nullptr` 成功：

```cpp
m_easyToShareContext.erase(it);
if (context && context->activeUsers > 0) {
    context->activeUsers -= 1;
}
```

`resetShareOnEasyIfNeeded()` 调用 `curl_easy_setopt(easy, CURLOPT_SHARE, nullptr)` 后忽略返回码，并直接把内部状态改为未绑定：

```cpp
curl_easy_setopt(easy, CURLOPT_SHARE, nullptr);
it.value() = false;
```

多处 cleanup 也忽略 `curl_share_cleanup()` 返回值，并立即清空指针：

```cpp
curl_share_cleanup(context->share);
context->share = nullptr;
```

独立 `/tmp` libcurl 最小复现已经确认：easy 仍绑定 share 时调用 `curl_share_cleanup()` 返回 `CURLSHE_IN_USE(2)`；只有先成功解除 easy 的 `CURLOPT_SHARE`，cleanup 才返回 `CURLSHE_OK(0)`。

**为什么是 P0**

libcurl share handle 的生命周期不是 QCurl 内部计数能单方面决定的。当前实现可能出现：

- QCurl 内部认为 `activeUsers == 0`，但 libcurl easy 仍绑定 share。
- `curl_share_cleanup()` 返回 `CURLSHE_IN_USE` 被忽略，QCurl 仍清空 share 指针。
- 旧 easy 继续引用已失去 QCurl 跟踪的 share。
- share lock/unlock callback 的 userdata 指向可能已销毁的 `ShareContext`。

这属于悬空 callback userdata 与对象图丢失问题，必须按内存安全缺陷处理。

**唯一修复路线**

1. `activeUsers` 改名并收敛为“真实绑定计数”，只在 `CURLOPT_SHARE` 绑定成功后增加。
2. 只有 `CURLOPT_SHARE=nullptr` 返回 `CURLE_OK` 后才能减少真实绑定计数。
3. 解绑失败时进入 `SharePoisoned` 或 manager poison 状态，保留 easy、share、context 和 callback userdata。
4. `curl_share_cleanup()` 必须检查 `CURLSHcode`。
5. 只有 `CURLSHE_OK` 才允许释放 context、清空 share 指针和删除 scope entry。
6. `CURLSHE_IN_USE`、`CURLSHE_INVALID` 和其他错误必须 fail closed，不能继续报告成功。
7. share 绑定、解绑和 cleanup 结果必须进入 release gate 的定点故障注入测试。

**完成标准**

- `CURLOPT_SHARE=nullptr` 失败时内部计数、map、context 和 share 全部保持可追踪。
- `curl_share_cleanup()` 非 `CURLSHE_OK` 时 context 不释放、指针不清空。
- ASan/UBSan/LSan 覆盖 share callback 后置触发，不出现 UAF。
- 负向测试覆盖 `CURLSHE_IN_USE`。

### P0-3 WebSocketPool 持有并异步解引用无失效协议的裸 `QCWebSocket*`

**位置**

- `src/private/QCWebSocketPoolPrivate_p.h:29`
- `src/private/QCWebSocketPoolPrivate_p.h:42`
- `src/QCWebSocketPool.cpp:88-99`
- `src/QCWebSocketPool.cpp:120-129`
- `src/QCWebSocketPool.cpp:158-184`
- `src/QCWebSocketPoolMaintenance.cpp:36-57`
- `src/QCWebSocketPoolValues.cpp:41-46`

**代码事实**

Pool 内部记录、反向索引和成功结果都保存裸指针：

```cpp
QCWebSocket *socket = nullptr;
QHash<QCWebSocket *, QUrl> socketToUrl;
```

`acquire()` 直接解引用池内指针：

```cpp
if (!conn.inUse && conn.socket->state() == QCWebSocket::State::Connected) {
    promise->addResult(QCWebSocketAcquireResult::success(conn.socket));
}
```

`clearPool()` 也直接调用旧指针：

```cpp
if (conn.socket->state() != QCWebSocket::State::Unconnected) {
    conn.socket->close();
}
conn.socket->deleteLater();
```

连接 timeout lambda 捕获裸 `socket`，5 秒后仍按裸指针查 map 和调用：

```cpp
QTimer::singleShot(kConnectionTimeout, this, [this, socket]() { ... });
```

本轮最小程序已经触发 ASan `heap-use-after-free`，栈顶为 `QCWebSocket::state()`，进入路径为 `QCWebSocketPool::clearPool()`。这与上述代码路径一致。

**为什么是 P0**

`QCWebSocket` 是 QObject。调用方拿到成功结果里的 `QCWebSocket*` 后可以合法 `delete socket` 或让其 parent 析构。当前 API 没有所有权句柄、借用句柄、禁止外部销毁的强约束，也没有连接 `QObject::destroyed` 清理索引。Pool 因此会在未来任一 acquire、clear、keepalive、cleanup、timeout 或 disconnected path 中解引用失效地址。

**唯一修复路线**

1. `PooledConnection::socket` 改为 `QPointer<QCWebSocket>`。
2. `socketToUrl` 的 key 也必须能处理 destroyed 后清理；不能以裸指针继续作为唯一真实性来源。
3. 创建 socket 时连接 `QObject::destroyed`，在 owner thread 中原子清理主索引、反向索引、pending promise、preWarm operation 和统计。
4. 所有解引用前检查 `QPointer`。
5. timeout lambda 捕获 `QPointer<QCWebSocket>`，并在回调开始处判空。
6. 成功结果固定为 pool-owned borrowed handle；result data 内部保存 `QPointer`，现有 `socket()` 在对象销毁后返回 `nullptr`。
7. 不引入 lease/token 第二路线。调用方提前删除 QObject 时，`destroyed` 协议必须安全摘除所有记录；文档只描述语义，不能替代运行时防护。

**完成标准**

- 外部 `delete` 池内 socket 后，后续 `acquire()`、`release()`、`clearPool()`、keepalive、cleanup 和 timeout 都不崩溃。
- pending future 收到结构化结果，不静默取消。
- ASan 覆盖外部删除、parent 删除、deleteLater、timeout 后删除和 signal slot 删除。
- Pool 内部不存在无 guard 的 `conn.socket->` 解引用。
- 已保存的 acquire result 在 socket 销毁后返回 `nullptr`，不暴露悬空地址。

## 六、P1：必须在发布前关闭的工程阻断

### P1-1 Pool 析构 signal 重入违反显式 value-result 合同

**位置**

- `src/QCWebSocketPool.cpp:49-63`
- `src/QCWebSocketPool.cpp:158-184`

**代码事实**

析构函数先遍历 pending promise，然后调用 `clearPool()`。`clearPool()` 在删除 socket 时会发射 `connectionClosed`。direct connection slot 可以同步重入 `acquire()`，当前对象尚未显式进入 `Destroying` 状态。

已复现结果：

```text
signal=1 initial_finished=1 initial_results=1 reentrant_started=1 reentrant_finished=1 reentrant_canceled=1 reentrant_results=0
```

也就是说，重入 future 最终被 Qt 取消，但没有返回 `PoolDestroyed` value result。

**为什么是 P1**

当前 public API 已经是 `QFuture<QCWebSocketAcquireResult>` / `QFuture<QCWebSocketPreWarmResult>`，库合同要求结构化 value result。析构期间把重入操作变成无业务结果的 Qt cancel，会让调用方无法区分 pool 销毁、调度失败、取消和 bug。

**唯一修复路线**

1. 增加 `Destroying` 状态，并在析构第一条语句设置。
2. `acquire()` / `preWarm()` 在 `Destroying` 下返回 already-finished future，业务结果为 `PoolDestroyed`。
3. `release()` / `clearPool()` / `setConfig()` 在 `Destroying` 下无副作用退出；query 返回 empty/default 或只读快照；timer/socket slot 立即退出。
4. 析构阶段只结算已存在 promise，不再创建 socket、promise、timer 或 network work。
5. 析构必须保留必要的 `connectionClosed` 可观察语义，但 direct slot 重入只能观察上述 Destroying 合同。

**完成标准**

- `connectionClosed` direct slot 中重入 `acquire()` 必须得到 `PoolDestroyed` result。
- 析构期间不创建新 socket、不 append pool、不启动 open。
- 每类 public API 和 timer/socket slot 都有具名 Destroying 测试；不要求 `void` 或 query API 返回不存在的 `PoolDestroyed` 值。

### P1-2 ABI promotion manifest 没有把关键输入绑定为不可变证据

**位置**

- `scripts/release_manifest.py:116-133`
- `scripts/run_release_gate.py:191-204`
- `scripts/qcurl_abi_gate.py:437-457`

**代码事实**

`release_manifest.py` 对 required artifact 的校验逻辑是：文件存在但没有 `sha256` 时不报错；只有 `sha256` 字段存在才比较 digest。

`run_release_gate.py` 登记 required artifact 时，如果文件存在才写入 `sha256`，不存在时仍能登记 `required=true`。

- `abi_hardbreak_current_snapshot`

6. CTest JUnit、libcurl consistency report、release install inventory、ASan/UBSan/LSan report、TSan report、UCE manifest、Doxygen 和 ABI/symbol report 等 release 必需机器证据必须使用稳定路径，并按 gate mode 作为外部 required artifact 绑定 path/kind/digest，不能只记录 gate 返回码。

**完成标准**

- required artifact 无 digest 时 `--verify-manifest` 非零。
- artifact 内容漂移时 verify 与 promote 均失败。
- 任意替换 old baseline、snapshot、report 或 library 时 promote 失败。
- manifest 除 digest 字段外任一内容变化都会使 canonical payload digest 验证失败。
- manifest 不含指向自身文件的普通 artifact entry；外部必需报告缺失或漂移均使 verify 失败。

### P1-5 WebSocket header backing storage 未绑定安全 teardown

**位置**

- `src/private/QCWebSocketLifecycle.cpp:101-113`
- `src/private/QCWebSocketLifecycle.cpp:411-419`

**代码事实**

SSL 错误路径调用 `curl_easy_getinfo(CURLINFO_SSL_VERIFYRESULT, ...)` 后忽略返回码：

```cpp
long verifyResult = 0;
curl_easy_getinfo(curl, CURLINFO_SSL_VERIFYRESULT, &verifyResult);
```

request header cleanup 先忽略 `CURLOPT_HTTPHEADER=nullptr` 的返回码，然后释放 slist：

```cpp
curl_easy_setopt(curl, CURLOPT_HTTPHEADER, nullptr);
curl_slist_free_all(requestHeaders);
requestHeaders = nullptr;
```

**分级结论**

`CURLOPT_HTTPHEADER=nullptr` 的返回码被忽略，且析构路径在 `removePersistentTransfer()` 前调用 `clearRequestHeaders()`。解绑失败后立即释放 slist，easy 可能继续引用已释放的 header list；这是 P1 ownership blocker。

`CURLINFO_SSL_VERIFYRESULT` 只在基础 `CURLcode` 已经表示 TLS 失败后查询。查询失败不会把 TLS 失败变成成功，缺失的是详细诊断。因此该部分应作为 P2 诊断完整性缺口处理，不能与 header UAF 风险使用同一严重度。

**唯一修复路线**

1. `CURLOPT_HTTPHEADER=nullptr` 必须检查 `CURLcode`。
2. request header slist 由 transfer/easy RAII owner 持有，只有成功解绑或 easy 已确认安全 cleanup 后才释放。
3. 解绑失败时进入 closing/poison 状态并保留 backing storage 到安全 teardown；不得选择进程期永久保留。
4. `CURLINFO_SSL_VERIFYRESULT` 失败传播“详细诊断不可用”，同时保留原始 TLS `CURLcode` 和失败结果。
5. ownership 相关 `setopt` 统一走 required adapter；诊断 `getinfo` 使用明确的 best-effort 结果，不伪造 `verifyResult=0` 为已验证。

**完成标准**

- 注入 header unbind 失败时不释放 slist。
- persistent transfer 摘除、easy cleanup 和 slist 释放顺序 exactly once。
- SSL verify getinfo 失败时 result/log/signal 明确表达详细诊断不可用，原 TLS failure 不变。
- ASan 覆盖 header backing storage 后置访问。

## 七、P2：必须补齐的边界与验证缺口

### P2-1 Pool 配置和 `preWarm()` 缺少统一输入边界

**位置**

- `src/QCWebSocketPoolValues.cpp:186-238`
- `src/QCWebSocketPool.cpp:198-219`

**代码事实**

`QCWebSocketPoolConfig` setter 直接接受输入值：

- `setMaxPoolSize(int value)`
- `setMaxIdleTime(int seconds)`
- `setMinIdleConnections(int value)`
- `setMaxTotalConnections(int value)`
- `setKeepAliveInterval(int seconds)`

这些 setter 没有拒绝负数、不可实现的跨字段关系或极大值。

`preWarm(count <= 0)` 返回成功：

```cpp
if (count <= 0) {
    return finishedFuture(QCWebSocketPreWarmResult::success(count, 0));
}
```

极大 `count` 会直接进入循环，创建同量 acquire/promise 链。

**为什么是 P2**

这是公共 API 边界问题。库不能把负数、`seconds * 1000` 的 signed overflow、极大连接数和不可实现的配置交给 Qt 或 libcurl 的版本相关行为兜底。Qt 对负 timer interval 的行为随版本变化，不能统一描述为 0ms timer；正确做法是在调用 `QTimer` 前完成验证。

**唯一修复路线**

1. 只保留一个 canonical config validator；构造、`setConfig()`、timer 启动和 `preWarm()` 都消费同一验证结果，不复制规则。
2. `maxPoolSize` 是 per-URL ceiling，`maxTotalConnections` 是 global ceiling，不强制 `maxPoolSize <= maxTotalConnections`；`minIdleConnections` 只需不超过可实现的 per-URL 有效上限。
3. 定义最大连接数、最大 preWarm count、最大 idle 秒数和 keepalive 秒数范围，并在乘 1000 前做有界转换。
4. `preWarm(0)` 固定为成功 no-op；负数、超过上限和非法配置返回 `InvalidArgument`，不能静默 clamp。
5. config mutation 返回结构化验证结果；无效新配置不得替换当前有效配置或启动 timer。

**完成标准**

- 负数、零、越界、可实现/不可实现跨字段组合和极大 count 均有测试。
- `preWarm(0)` 成功且不创建 acquire/promise；`preWarm(count<0)` 返回 `InvalidArgument`。
- 极大 count 不产生同量 promise/loop。
- keepalive 秒到毫秒转换不溢出，行为不依赖 Qt 对负 interval 的版本差异。

### P2-2 当前仍缺少外部可观察一致性的 live proof

本轮静态复核未新增 cache/Vary/Age/304 的 P0/P1，但这不等于最终证明已完成。以下 live parity 仍必须重跑：

- ordered raw headers 顺序、大小写和重复项。
- duplicate headers，尤其是 `Set-Cookie`、`Cache-Control`、`Vary`、`Date`、`Age`。
- 请求 cache directives：`no-store`、`no-cache`、`max-age=0`、`Pragma`。
- `Vary` 使用真实有效出站 header，而不是 request object 的期望值。
- `Date/Age/current-age` freshness 与饱和边界。
- 304 metadata merge 与 cached representation replay。
- redirect 链、body / stream upload、retry / idempotency 的外部可见一致性。
- scheduler / cancellation / exactly-once completion 的 direct-slot 重入压力。
- Cookie、Diagnostics、安装导出和 public ABI surface 的 fresh evidence。

这些项目不是当前新 blocker，但属于 final deep QA 前置门禁。

### P2-3 Finding 关闭与 release readiness 必须分层

单项 finding 使用以下状态机：

```text
OPEN -> REMEDIATED -> VERIFIED
```

- `OPEN`：当前代码仍存在缺陷或合同缺口。
- `REMEDIATED`：实现已修改且定点测试进入绿色，但证据尚未完整绑定当前身份。
- `VERIFIED`：对应负向测试、sanitizer、ABI 或 manifest 机器证据已通过并绑定当前实现。

单项 finding 不需要每次都运行完整 release QA 才能进入 `VERIFIED`；它需要与风险匹配的定点证据。全局 `READY_FOR_RELEASE` 则独立要求所有阻断均为 `VERIFIED`，并完成完整 final deep QA。这样既允许逐项闭环，也不会把局部 PASS 误写成发布 PASS。

## 九、外部可观察一致性复核要求

QCurl 是 libcurl 到 Qt6/C++ 的 binding。判断是否合格不能只看内部实现是否“更 Qt”，必须证明调用方可观察行为与 libcurl/HTTP 语义一致。

### 9.1 HTTP/Reply

必须证明：

- status code、reason、body bytes、ordered raw headers 与 direct libcurl 对齐。
- 重复 header 不被 `QMap` 或最后值覆盖破坏。
- redirect 之后的最终响应与中间响应记录边界明确。
- streaming body 与 upload source 的 lifetime 不依赖 caller 局部变量。
- retry 只在 method、body 可重放和 idempotency 合同允许时发生。
- cancel、timeout、manager destroyed 和 reply destroyed 都恰好完成一次。

### 9.2 Cache / RFC 9111

必须证明：

- cache admission 只消费 ordered raw response headers。
- `Vary` 使用真实有效出站 header。
- `Set-Cookie` 网络可观察，但不进入 response cache，不在 cache hit 重放。
- `Date`、`Age`、freshness 使用饱和运算。
- 304 merge 只更新允许合并的 metadata，不重写不可合并字段。
- 磁盘 cache 对损坏文件先验限长，再解析。

### 9.3 WebSocket

必须证明：

- persistent CONNECT_ONLY 在 send/recv 使用期留在 multi。
- `curl_easy_send()` / `curl_easy_recv()` 的 EAGAIN、partial frame、close frame 和错误映射正确。
- request header slist、callback userdata、frame buffer 和 socket object 的生命周期受控。
- Pool 不因外部删除、析构 reentry、timer 回调和 keepalive deadline 产生悬空指针。

### 9.4 Release / ABI

必须证明：

- 正式 shared library 没有 test hook 符号和环境变量控制面。
- Core public ABI 只包含 public surface manifest 允许的符号。
- Other Extras 作为 Preview 也必须通过安全、线程和安装门禁。
- candidate manifest、promotion manifest、final manifest 均绑定同一组不可变 authority、artifact digest、工具链、HEAD 和 build dirs。
- 正式 full/promotion/final 命令必须同时传入 `--build-dir`、`--static-build-dir` 与 `--test-build-dir`；前两者的 `BUILD_TESTING` 必须为 `OFF`，test tree 必须为 `ON`，三棵树及其关键 CMake capability 都进入 identity。
- release install/consumer/symbol/string/ABI step 必须读取 OFF producer tree；test tree 只承载 CTest、libcurl consistency、白盒故障注入、生命周期和 sanitizer harness。路由错误必须在执行任何 gate 前 fail closed。

## 十、唯一整改路线

当前不得继续旧 T7/T8，也不得询问 Git 授权。修订后的活跃方案包从 T5 开始，固定走以下路线。

### 10.1 重基线 authority 与状态

- 保持 release 状态为 `NOT READY FOR RELEASE`。
- 本文作为 finding/verdict SSOT，但明确排除在 release identity authority digest 之外。
- release identity authority 恰好为 active requirements、plan、contract 与 v2 release contract。
- 撤销旧 `MANIFEST_SSOT_LOCKED`、`ABI_PIPELINE_LOCKED` 和 `WAITING_FOR_GIT_AUTHORIZATION`。
- 旧 `READY_FOR_RELEASE`、旧 closeout、旧 QA 和旧 manifest 不得用于当前候选。

### 10.2 T5-T6：正式库纯度与 share ownership

1. 正式 target 永不定义 `QCURL_ENABLE_TEST_HOOKS`；测试使用已存在且不安装的 companion。
2. `BUILD_TESTING=OFF` release tree 提供发行/ABI/consumer 证据；`BUILD_TESTING=ON` test tree 提供 CTest、故障注入和 sanitizer。
3. share bind、detach、cleanup 只由 libcurl 返回码推进状态；失败时保留并 poison 完整对象图。

### 10.3 T7：Pool 生命周期与输入边界

1. Pool 采用 `QPointer` backed borrowed handle；连接 `QObject::destroyed` 并原子清理索引和 operation。
2. 析构第一步进入 `Destroying`；future API 返回 `PoolDestroyed`，void/query/slot 按 API 类别 no-op 或返回空值。
3. 配置统一经过 canonical validator；`preWarm(0)` 成功 no-op，负数/超限为 `InvalidArgument`，timer 转换有界。

### 10.4 T8：WebSocket backing storage 与 ABI 边界

1. header slist 由 transfer/easy RAII owner 持有到安全 teardown；解绑失败不得释放 backing storage。
2. SSL verify getinfo 失败只传播详细诊断不可用，保留原 TLS failure。
3. 从 Core public ABI 移除 `QCCurlMultiManager` owner，只保留 opaque persistent-transfer bridge。

### 10.5 T9：release evidence fail closed

1. required artifact 必须存在且具有非空 digest。
2. full/promotion/final authority 必须严格四件套；empty/fewer/more/alias 全部失败。
3. manifest 不把自身登记为普通 required artifact；外部 artifact 使用文件 SHA-256，manifest 使用排除自身 digest 字段后的 canonical payload digest。
4. CTest、libcurl parity、release install inventory、sanitizer、UCE、Doxygen、ABI 与 symbol report 均作为外部 required artifact 绑定。
5. promotion 的 library、v1 baseline、candidate snapshot、hard-break report 和 manifest path/digest 必须与 manifest 证据对等。

### 10.6 T10-T11：提交、promotion 与 final QA

只有 T5-T9 全部进入 `VERIFIED`，且 pre-commit deep QA 通过后，才能请求两个本地提交授权。获得授权后依次执行：

1. clean candidate commit。
2. promotion-candidate full gate。
3. v2 baseline promote。
4. baseline-only commit。
5. fresh final current full gate。
6. `READY_FOR_RELEASE` 本地终态。

final QA 必须使用全新的 `BUILD_TESTING=OFF` release shared/static tree 和 `BUILD_TESTING=ON` test/Clang/sanitizer tree，并重跑 HTTP/cache/WebSocket/Cookie/Diagnostics/scheduler/cancellation live proof。
release manifest 必须同时绑定三类 build dir 及其 CMake capability；不得在无测试的 OFF tree 上生成伪 full CTest 证据。

tag、push、GitHub Release 和资产上传仍不在当前合同内。

## 十一、回滚、止损与证伪条件

### 11.1 回滚原则

- 任一修复切片无法证明不变量时，停止在该 finding 的 `OPEN/REMEDIATED` 状态，release 保持 `NOT READY`；不得自动 reset、restore 或覆盖用户 dirty WIP。
- 不用关闭 WebSocket、关闭 Other Extras、关闭测试、开启兼容 shim 或刷新 baseline 来掩盖失败。
- 不把 preview 标签当作安全豁免。
- 不把 old build tree 的通过结果迁移到新 HEAD。

### 11.2 止损规则

出现以下任一情况立即停止发布推进：

- 正式 shared library 仍包含 `QCURL_TEST_FORCE_*` 或 `ForTest/ForTesting` 符号。
- 任一 easy 在 share 解绑失败后被内部计数视为已解绑。
- 任一 `curl_share_cleanup()` 非 `CURLSHE_OK` 后仍释放 context。
- Pool 中任一裸 socket 在外部删除后仍可被 timer、clear 或 acquire 解引用。
- 析构重入 future 没有业务 result。
- manifest required artifact 无 digest 仍通过。
- full/promotion/final 无四件套 authority 仍能构造 release manifest。
- ABI promotion 可替换 old baseline、snapshot、report 或 library。
- Core ABI allowlist 仍以内部类 owner 通配放行。
- manifest canonical payload digest 缺失、不可重算或内容漂移仍通过。

### 11.3 证伪条件

要推翻本文 P0/P1/P2，必须提供当前 HEAD 的机器证据，而不是人工解释：

- 精确源码 diff。
- 新 build 目录。
- `BUILD_TESTING=OFF` 正式库符号和字符串证据。
- ASan/UBSan/LSan/TSan 对应测试。
- release manifest verify 与 negative tests。
- ABI dynamic symbol allowlist 与 hard-break/current diff。
- HTTP/libcurl consistency live proof。

单项 finding 由与其风险匹配的证据决定是否进入 `VERIFIED`；不要求每次定点关闭都运行上述全部类别。全局 release PASS 必须具备完整矩阵，缺少任一全局门禁时只能保持 `NOT READY FOR RELEASE`。

## 十四、最终结论

QCurl 的 2.0.0 方向是正确的：允许 hard-break、收敛 ordered raw header cache route、拆分 ABI current/promotion-candidate、明确 v1 到 v2 的 release identity，这些都是必要步骤。

但当前候选还没有达到企业级 Qt6/C++ 网络库发布标准。最核心的问题不是功能是否完整，而是以下合同仍未闭合：

- 正式库与测试故障注入隔离。
- libcurl share/easy 真实绑定生命周期。
- QObject 指针失效与 direct signal reentry。
- WebSocket option backing storage 与安全 getinfo 错误传播。
- release manifest、authority、artifact digest 和 ABI promotion 的供应链不可变性。
- public ABI 中内部实现类型的最小化。
- public config 输入边界与容量安全。
- HTTP/cache/WebSocket/Cookie/Diagnostics 的外部可观察一致性 fresh proof。

因此，当前 release 2.0.0 必须继续停在 **NOT READY FOR RELEASE**。活跃方案包已退回 `REMEDIATION_REQUIRED`，下一步从 T5 开始，依次关闭正式库纯度、share ownership、Pool 生命周期、WebSocket/ABI 边界和 release evidence；T5-T9 与 pre-commit deep QA 完成前不得进入提交授权、promotion 或 final QA。历史 PASS、旧 build tree、Preview 标签、关闭默认能力、兼容 shim、宽松 manifest 或手工 baseline promotion 都不能替代这个闭环。
