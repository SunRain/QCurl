# QCurl 对 `legendary-python` 移植的技术尽调

这是维护者评估网络底座与业务分层的案例，不是入门教程，也不代表某个下游版本已经完成验收。本文只维护可复用的职责、风险与推进条件，不累积历史回归数字、报价或一次性执行记录。

## 1. 结论与职责分层

QCurl 可以承担移植中的通用网络基础设施，但不应吸收 Epic 或 `legendary` 专属语义。按下面三层分工，不另建一套平行的能力与边界清单：

| 层次 | 应承担的职责 | 不应越过的边界 |
| --- | --- | --- |
| QCurl 网络原语 | HTTP/HTTPS 与版本选择；请求 header/auth/timeout/proxy；cookie jar、导入导出与持久化；连接复用、调度和并发管理；流式上传/下载、取消与通用重试；错误、日志与诊断基础 | 不实现特定端点 API、token 生命周期决策或安装策略 |
| 移植项目网络适配 | EGS/LGD 的 REST/GraphQL 客户端；OAuth、设备码和 Web 登录桥接；token 刷新与持久化、cookie/XSRF 会话策略；领域错误映射与业务级限流、重试分类 | 面向 UI/CLI 输出领域结果，不把业务包装层回灌 QCurl |
| 下载与安装域 | manifest/chunk 管理、解析与校验；下载编排、恢复和重试策略；安装目录、文件落盘与用户交互 | 不将校验、安装事务与底层网络执行耦合 |

WebSocket 对这一移植不构成阻断，仅是附加能力；HTTP/3 是否成为业务交付门槛由移植项目决定。组件 opt-in、Preview 成熟度及 API/ABI 边界遵循[正式发布合同](../release/2.0.0-hard-break-release-contract.md)，不能把网络能力列表当作所有组件均有同等稳定性。

## 2. 实施前要确认的条件

1. 目标平台矩阵与 Qt 版本。
2. 是否需要 Qt WebEngine 或其他 Web 登录方案，以及它与 QCurl 的会话桥接方式。
3. token/cookie 的持久化介质和生命周期归属。
4. 下载目录、校验与恢复口径。
5. HTTP/3 是可选能力还是明确交付门槛。

这些决定应在移植项目中落实，不通过扩展 QCurl 的职责绕过。

## 3. 主要风险

- **低风险**：以 QCurl 承接通用 HTTP、认证头、cookie、代理和 timeout。
- **中风险**：Web 登录与 Qt cookie/profile 的双向同步，以及业务重试、限流和错误分类是否需要更细的策略。
- **高风险**：把 Epic 专属语义写入 QCurl，或让下载校验和安装过程依赖网络层内部状态。

## 4. 推进顺序与依据

先确认分层，用 QCurl 跑通登录、基本 API 调用与一次完整下载；再固化 cookie/token 持久化并建立可离线回归的关键验证；最后评估 HTTP/3、额外诊断和交付优化。上层恢复策略不能仅凭底层请求重试通过就认定完成。

能力判断以当前 `src/`、`tests/qcurl/` 和 `tests/libcurl_consistency/` 为依据，验证方式见[构建与测试](../build-and-test.md)。移植项目自己的详细职责矩阵与任务分解留在该项目，不在本文持续追加。
